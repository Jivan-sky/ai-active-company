我先说清楚一件事：我加载的 `kb-retrieval-acceptance` 这张卡**不管你现在问的这件事**。它管的是「已经决定叠一层自托管检索层之后，这条链路能不能用」的验收，前提是手上已经有语料。你问的是它**上游**的语料整理，属于「输入不成立」那一档。所以下面不是那张卡的流程，是我按你三个问题直接给的建议——不过有一条纪律我会从那边借过来，因为它正好是这三个问题的共同落点。

## 先把判据说死：整理到位 = 你写得出「篇 + 位置」

这是整件事的验收线：随便挑一个你们业务上真正关键的主张（比如"年假怎么折算"），你能不能在语料里指出**哪一篇、哪一章/哪一节**写着它。

写得出 → 语料算整理完了，目录和路由表都只是这个事实的载体。
写不出 → 还没整理完，别急着上检索层。先跑检索再回头补出处，答案是会漂的。

你把这条当验收线，下面三个问题的很多设计取舍会自己定下来。

## 一、目录：分三层，原件层只增不改

关键不是"树长得像不像人的分类习惯"，而是**哪些能重建、哪些不能**。

```
kb/
  raw/          # 原件层：只增不改，永不就地编辑
    <域>/<年>/<文件>
  work/         # 加工层：抽文本、切块、索引——全部可由 raw 重跑
    text/  chunks/  index/
  meta/
    manifest.yaml   # 路由表 / 文档清单
  tests/
    questions.md    # 「问题 | 出处」对拍集
```

- `raw/` 里一个字节都别动。理由是对拍：你的判据是拿答案回原文**逐字**比，一旦就地编辑，比对基准就没了。
- `work/` 整个可以删掉重建。判断某个东西该放哪层，就问一句"删了它，我能不能从 raw 重跑出来"。
- 目录嵌套别超过三层，而且只编码你**真的会拿来筛**的轴（域、文档类型、年份）。为了好看做的分类层级，检索用不上，人也不看。

## 二、路由表：路径不是主键，版本关系才是

我的理解是你说的是那个「文档 → 位置/元数据」的总清单。如果你们说的路由表是别的意思，纠我一下。

最要命的一条：**别拿文件路径当主键**。路径一定会变（重组目录、换命名），一换，历史引用就全指向虚空，而且你查不出它当时指的是哪份。给每份文档一个稳定 ID。

```yaml
- id: pol-leave-2024          # 稳定主键，路径变了它不变
  title: 员工休假管理办法
  path: raw/hr/2024/leave-v3.pdf
  domain: HR
  type: policy                # policy / spec / faq / minutes
  status: 现行                # 现行 / 废止 / 草稿
  version: 3
  effective_from: 2024-07-01
  supersedes: pol-leave-2021  # ← 载荷在这两行
  superseded_by: null
  owner: HR-王XX
  acl: [hr, all-staff]        # 谁能看
  origin: 钉钉群/2024-06-20    # 从哪进来的
  ingested_at: 2026-10-14
  extractor: pdfplumber-0.11  # 抽取工具+版本，保证可复现
```

`supersedes / superseded_by` 是这张表里唯一非填不可的"额外"字段。原因：**同一主题的新旧两版同时在库里，是检索最危险的失败形态**——而且向量通道和关键词通道可能各自独立地偏向旧版。你把版本关系显式写下来，才有本事在事后数出"有多少条被旧版压掉了"。这是不能靠 prompt 或模型能力兜住的，只能靠元数据。

`acl` 那栏看你们有没有跨部门隔离要求——如果有，权限必须在元数据这一层就标出来，不能等展示层再挡。

## 三、原件怎么留

四条：

1. **动字节就别动原件，改版 = 新对象。** 旧版留着，标 `status: 废止` + `effective_to`，让检索去降权。**不要删旧版**——删了就永远测不出上面说的旧版压制。
2. **记抽取工具和版本。** 同一份 PDF 换个解析器，抽出来的文本就变了，你的对拍结果跟着变，事后没法复现。这条最容易被漏。
3. **记来源和摄入时间。** 出问题时要能回溯"谁、什么时候、从哪放进来的"。
4. **原件保真优先于体积。** 扫描件、群聊导出、网页存档，形态各不相同——`raw/` 保留它们的原始形态，别在入口处就转格式。
