**污染原因**：同一份卡在文件系统上另有副本（仓库 `skill/kb-retrieval-acceptance/` 与带卡 HOME 各一份），基线臂里模型用 `find` 就能翻到 —— 所以「不带卡」不成立。**干净的基线需要把这两处一并隔离**，本轮没做到。

**三条干净对照的结论（这条是负面的，必须留着）**

- **基线也给出方向正确的答案。** 第 1 条基线自己就指出「测的是像不像人话不是对不对」、要造评测集、要把检索与生成分开评、要留 hold-out；第 2 条基线自己就得出「大概率不是 rerank 的问题」。**所以卡的价值不是「救错」，是「收敛」**：把一套发散的好建议，收敛成一份**能判红、有判停、能交付**的流程，并强制带上口径声明。
- **基线里有卡没有的好东西**，应当吸收：
  1. **三变体消融**（同批 case 分别跑「只用 Top1」「用现在的全量 context」「强制把 gold 置顶」，看差异）—— 比卡里「先换更大模型」更能定位问题；
  2. **doc 级命中 vs chunk 级 context 的错位**：卡判的是「Top1 是不是那篇源文档」（盘级），而生成吃的是 **chunk**；答案句在相邻 chunk 时，会出现「盘对了、chunk 不含答案句」的第三种形态。卡的 E4 目前**只覆盖盘级**。
  3. 基线的指标口径（recall@k / MRR / nDCG / context recall）在**多域、大语料**时比本卡的「Top1 命中率」更合适。
- **第 3 条暴露的缺口**：卡正确地把「选型 / 分档」挡在门外，但**只挡不导** —— 用户问「该不该上」时，卡给了边界却不给去处（那个上游议题还没定）。

### 5.3 独立复核（不信自报数）

复核不是重跑一遍，是**换一条通道重取**：不走 chat 的引用列表，直接打检索接口对同一批问句取排序。

**（a）Top1 归属：10/10 与自报一致。** 逐题 Top1 文档与报告完全相同（v1→04、v2→04、v3→01、v4→04、v5/v6/v7→03、v8/v9/v10→04）；同一问句连跑三次结果逐字节相同（确定性）。报告「指定源 `02` 在全部题里从未排到第 1」**成立**。

**（b）根因措辞要改。** 报告称「运行进程里没有 rerank 服务」。实测是：**配置写着 `enable_rerank: true`，但模型槽是空的**（`rerank_model=""`）。运行日志逐字为：

```
stage=Rerank   action=skip     reason="empty_model_id"
stage=Merge    action=fallback reason="empty_rerank_result"
stage=FilterTopK action=input  merge_cnt=8 rerank_cnt=0 search_cnt=8
```

代码侧对应 `chat_pipeline/rerank.go`：模型 ID 为空 → `RerankOutcomeNoModel` → 记 warn 后**保留检索原序**继续。模型注册表实测只有 2 个（`Embedding` / `KnowledgeQA`），确无 Rerank 类型。
→ **结论不变**（rerank 实际没生效），但归因应是「**开着却没模型**」，不是「没开」。这条差别重要：它决定该修的是「补模型」还是「把开关关掉」。

**（c）分通道拆开看，根因比报告写的更深一层。** 把检索的两个通道分别关掉，跑同一批题：

| 通道 | Top1 命中 | 失败形态 |
|---|---|---|
| 融合（卡实际吃的） | 6/10 | — |
| 关键词单通道 | 6/10 | 版本类题偏向旧版 |
| 向量单通道 | **3/10** | 几乎恒把 `04-异常情况处置` 的摘要块顶到第 1（原始分 0.62–0.79） |

**向量通道比关键词通道更差，还在拖融合分。** 更硬的一条机制：四篇文档各有一个自动生成的 `# Summary` 块，在向量通道里**摘要块恒压过正文块**；四篇摘要彼此挤在 0.57–0.64 的窄带里几乎不可分，而**指定源 `02` 的摘要是四篇里最低的那个**（0.5667）。这就是「`02` 系统性从不排第一」的机制：它的摘要块在向量通道先天吃亏，正文块又被别篇的摘要块盖住。

**（d）报告两处数字口径要修正。**

- 「命中分数全挤在 0.9–1.0」：0.9–1.0 是**融合后**的分数；**未融合的向量原始分只有 0.58–0.79**，关键词原始分才是 1.0 / 0.9x。**挤压是融合口径造成的，不是嵌入模型原始分的分布。**
- v2 / v9 / v10 三条的分数尾数（报告 0.99 / 0.995 / 1.000，实测 0.9773 / 0.9839 / 0.9905）不一致；**文档归属不受影响**。原因是 chat 路径在检索前先做 **query 改写**（配置 `enable_rewrite: true` / `enable_query_expansion: true`）：日志实测问句「访客扫码登记失败时应该怎么处理？」被改写成「访客扫码登记失败时的处理方法是什么」。我复核时用的是**原始问句**，所以有微小偏移。

  ⚠️ 这条带出一个硬要求：**评测必须记录「实际送去检索的 query」**，否则别人复现不出来（见 §6 第 7 条）。

**（e）为什么生成还是 10/10 —— 因为检索层在这套语料上等于没起作用。**

逐条查 11 个回合的引用列表：**11/11 都是同一组 8 块**（4 篇 × 每篇 2 块 = **整库全量**，而检索返回上限恰好是 8）。也就是说，**无论问什么，整库都被塞进了 context**，排序对不对根本不影响生成。

所以 10/10 **不含任何检索能力信息** —— 它不是「检索其实也没那么差」的证据，而是「本次测不出检索的坏影响」。同一机制也让「融合 6/10」这个数**偏乐观**：它是在一个检索失效与否都不改变结果的语料上量出来的。

→ 这条给 E1 出题加了一条硬约束：**语料规模必须大于检索返回上限**，否则整套测试对检索不敏感（见 §6 第 8 条）。

### 5.5 顺带发现：被测平台自带评测子系统（本轮没用上）

被测的自托管检索层**自带一套评测接口**：按 dataset 驱动，指标含 Precision / Recall / NDCG@3 / NDCG@10 / MRR / MAP + BLEU / ROUGE，走 `POST /api/v1/evaluation`。
本轮的 E4 是**手搓的 Top1 判法**。下一轮应评估改吃平台原生评测：它能给 MRR / NDCG 这类**排序**指标（比二元 Top1 更能暴露 §5.3c 那种「排序坏、但都进了 top-k」），而且运维侧能自行复现。
